## 1. 큰 Tick 함수는 언제 작은 시스템으로 나누나?

한 `HandleTick` 안에 이동, 교전 확인, 자동 시전이 전부 들어가면 코드를 읽는 사람이 전체 흐름을 계속 머릿속에 올려야 한다.
이때 작은 시스템으로 나누면 한 번에 보는 일이 줄어든다.

Phase 3에서는 Tick 흐름을 이렇게 나눴다.

| 시스템 | 맡은 일 |
|--------|---------|
| `MovementSystem` | 움직임 처리 |
| `EngagementSystem` | 적과 만났는지 확인 |
| `CastingSystem` | 무공을 쓸지 결정 |

핵심은 파일을 나누는 것이 아니다.
**각 코드가 맡은 일을 하나로 줄이는 것**이 핵심이다.

Phase 1에서는 움직임과 도달 확인 정도라 메서드 분리로 충분했다.
Phase 3에서는 자동 시전까지 들어오면서 Tick 안의 일이 3개가 됐다.
이때부터 작은 시스템으로 나누는 이득이 생긴다.

> [!important]
> 좋은 분리는 미래에 좋아 보이는 구조가 아니라, 지금 읽기 어려워진 지점을 실제로 줄이는 구조다.

## 2. 같은 데이터도 왜 역할에 따라 다르게 들고 있나?

`BattleContext`와 `ActorView`는 비슷한 전투 데이터를 담지만 역할이 반대다.

| 구분 | `BattleContext` | `ActorView` / `BattleSnapshot` |
|------|-----------------|--------------------------------|
| 역할 | 전투 계산용 현재 상태 | 화면 표시용 사본 |
| 바뀌는가 | 바뀐다 | 안 바뀐다 |
| 쓰는 곳 | Engine과 System | View |
| 목적 | 다음 Tick을 계산한다 | 안전하게 보여준다 |

`BattleContext`는 시스템들이 같이 밀고 가는 상태다.
`MovementSystem`이 위치를 바꾸면 `EngagementSystem`도 그 바뀐 위치를 봐야 한다.

`ActorView`는 화면에 넘겨주는 사본이다.
View가 그리는 동안 Engine이 다음 Tick을 진행해도, 이미 넘긴 화면 데이터는 흔들리지 않아야 한다.

> [!note]
> 여기서 배울 점은 "class가 좋다" 또는 "struct가 좋다"가 아니다.
> **데이터가 맡은 역할에 따라 바뀌어야 하는지, 고정되어야 하는지를 먼저 정한다**는 점이다.

## 3. 왜 고르는 코드와 실제로 바꾸는 코드를 나누나?

`CastingSystem`은 어떤 무공을 쓸지 고른다.
`ISkillExecutor.TryCast`는 실제 시전 처리를 한다.

| 구분 | 맡은 일 |
|------|---------|
| `CastingSystem` | 슬롯 순서, 쿨다운, 거리 조건을 보고 무공을 고른다 |
| `TryCast` | 내공 차감, 쿨다운 설정, 기세 획득, 이벤트 발행을 처리한다 |

이 분리는 앞으로도 계속 중요하다.

- 자동 시전은 `CastingSystem`이 고른다.
- 나중에 단축키로 무공을 써도 `TryCast`를 지나가야 한다.
- 오의나 특수 행동이 생겨도 최종 실행 규칙은 한곳에 모인다.

> [!important]
> 고르는 곳과 실제로 바꾸는 곳을 나누면, 비용 차감과 이벤트 발행 같은 규칙을 한곳에서 지킬 수 있다.

## 4. 슬롯 순서는 왜 우선순위가 되나?

자동 시전은 여러 후보 중 하나를 고르는 문제다.

Phase 3의 선택 기준은 단순하다.

1. 슬롯을 위에서부터 본다.
2. 조건이 맞지 않으면 다음 슬롯으로 간다.
3. 처음 조건이 맞는 무공을 시전한다.
4. 그 Tick에서는 더 보지 않는다.

이 규칙에서 슬롯 순서는 곧 우선순위다.
사용자가 슬롯을 바꾸면 자동 시전 판단도 바뀐다.

> [!note] 다른 방법
> 각 무공에 점수를 매겨 가장 좋은 무공을 고르는 방식도 있다.
> 하지만 Phase 3에서는 슬롯 순서가 더 쉽고, 예측 가능하고, 테스트하기 좋다.

## 5. 같은 입력이면 같은 결과가 나와야 하는 이유는?

결정성은 **같은 입력이면 같은 결과가 나오는 성질**이다.

같은 슬롯, 같은 적, 같은 시간 흐름이면 같은 무공 시전 순서가 나와야 한다.
그래야 테스트가 믿을 만하고, 버그를 다시 재현할 수 있다.

지금 자동 시전에는 난수가 없어서 결정성 테스트가 당연해 보일 수 있다.
그래도 테스트를 두면 나중에 누군가 랜덤 선택을 넣는 순간 바로 알 수 있다.

> [!note]
> 어떤 테스트는 지금 버그를 찾기 위해 존재한다.
> 어떤 테스트는 앞으로도 깨지면 안 되는 규칙을 지키기 위해 존재한다.

## 6. 실패할 때 아무것도 바꾸지 않는 게 왜 중요한가?

원자적 처리는 **성공하면 전부 처리하고, 실패하면 아무것도 바꾸지 않는 것**이다.

무공 시전은 여러 일이 함께 일어난다.

- 내공을 쓴다.
- 쿨다운을 건다.
- 기세를 올린다.
- 시전 이벤트를 보낸다.

내공이 부족하면 이 중 아무것도 일어나면 안 된다.
내공만 깎이고 시전은 실패하거나, 쿨다운만 걸리고 이벤트가 안 나가면 상태가 꼬인다.

그래서 `TryCast` 같은 한 진입점이 중요하다.
여러 곳에서 조금씩 상태를 바꾸면 실패 처리가 흩어진다.

## 7. 지금 필요 없는 코드를 만들지 않는 이유는?

YAGNI는 "You Aren't Gonna Need It"의 줄임말이다.
쉽게 말하면 **지금 필요 없는 코드는 지금 만들지 말자**는 원칙이다.

Phase 3에서 일부러 만들지 않은 것들이 있다.

| 안 만든 것 | 안 만든 이유 |
|------------|--------------|
| `SkillEffect` 타입 | 실제 효과 처리는 Phase 4에서 시작한다 |
| 심법 중복 skip | 효과 시스템이 아직 없어서 판단할 수 없다 |
| 시스템 DI 등록 | 아직 교체하거나 Mock으로 바꿀 필요가 없다 |

미리 만든 코드는 공짜가 아니다.
읽어야 하고, 테스트해야 하고, 나중에 바뀐 설계와 충돌할 수 있다.

> [!important]
> "언젠가 필요할 것 같음"과 "지금 필요함"을 구분하는 습관은 유지보수 비용을 줄인다.

## 8. 설계 문장을 코드에 그대로 베끼면 왜 위험한가?

SSOT는 전투 설계의 진실이다.
하지만 SSOT의 문장을 코드에 그대로 베끼는 게 항상 정답은 아니다.

| SSOT 표현 | 코드 판단 | 이유 |
|-----------|-----------|------|
| `skillSlots[]`와 `skillCooldowns[]` | `SkillSlot` 하나로 묶음 | 서로 같이 움직이는 값이라 따로 두면 실수하기 쉽다 |
| `target.position` | 실제 거리로 해석 | 이 게임의 축에서는 절대 좌표보다 거리 판단이 맞다 |

여기서 보존해야 하는 것은 문장 모양이 아니라 동작의 의미다.

**SSOT는 동작을 정하고, 코드는 그 동작을 가장 안전하게 표현해야 한다.**

> [!warning] 조심할 점
> SSOT와 다른 구현을 마음대로 해도 된다는 뜻은 아니다.
> 의미가 모호하거나 코드 표현이 위험할 때는 판단 이유를 문서에 남기고, 필요하면 SSOT도 고쳐야 한다.

## 9. 이름 변경이 왜 설계 변경일 수 있나?

Phase 1/2에서는 적 도달을 `Resolve`에 가깝게 봤다.
Phase 3에서는 `Engage`가 됐다.

이건 단순한 이름 변경이 아니다.

| 이전 의미 | 새 의미 |
|-----------|---------|
| 적에게 도달하면 전투가 끝난다 | 적에게 도달하면 교전이 시작된다 |

의미가 바뀌면 테스트 기대값도 바뀐다.

테스트가 깨졌을 때는 먼저 이걸 나눠 봐야 한다.

1. 코드가 사양을 어긴 것인가?
2. 사양이 바뀌어서 테스트 기대값이 낡은 것인가?

Phase 3은 두 번째였다.

## 10. 빈 배열과 `null`은 의미가 어떻게 다른가?

`Array.Empty<T>()`는 길이가 0인 배열을 만든다.
`null`과 다르다.

| 표현 | 뜻 |
|------|----|
| `null` | 목록 자체가 없다 |
| `Array.Empty<T>()` | 목록은 있는데 항목이 0개다 |

`ActorView.Skills`처럼 읽기만 하는 목록은 `null`보다 빈 배열이 편하다.

```csharp
foreach (var skill in actor.Skills)
{
    // 빈 배열이면 본문이 실행되지 않는다.
}
```

받는 쪽에서 `if (actor.Skills != null)` 같은 방어 코드를 덜 쓰게 된다.

단, 입력이 꼭 있어야 하는 자리까지 빈 배열로 숨기면 안 된다.
빈 배열은 "정상적으로 비어 있음"을 나타낼 때만 쓴다.
