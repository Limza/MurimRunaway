## 1. 행동 뒤의 결과는 어디서 확정해야 하나?

결과가 있는 시스템은 행동만 실행하고 끝나지 않는다.
행동이 만든 상태 변화를 언제 확정할지도 정해야 한다.

Phase 4부터 전투에는 이런 결과가 생긴다.

| 원인 | 결과 |
|------|------|
| 적 일반 공격 | Player HP 감소 |
| 무공 데미지 | Enemy HP 감소 |
| HP 0 | 사망 |
| 모든 적 사망 | 승리 |
| Player 사망 | 패배 |

중요한 점은 데미지, 사망, 승패가 모두 같은 무게의 작업이 아니라는 것이다.
데미지는 여러 시스템이 만들 수 있지만,
사망과 승패는 전투 전체의 상태를 바꾸는 확정 단계다.

> [!important]
> 결과가 있는 시스템에서는 "무엇을 할까?"만큼
> "그 결과를 어디서 확정할까?"가 중요하다.

이번 코드에서는 Tick 끝에서 사망과 승패를 정리한다.
그래서 시스템 중간에 승패가 어중간하게 확정되는 일을 줄인다.

## 2. 거리 조건과 타겟 범위는 왜 다른가?

거리 조건은 "행동할 수 있는가?"를 판단한다.
타겟 범위는 "누가 영향을 받는가?"를 고른다.

| 이름 | 뜻 |
|------|----|
| `EngageDistance` | 이 거리 안이면 교전하거나 공격할 수 있다 |
| `SkillRange.Single` | 가장 앞의 적 1명 |
| `SkillRange.NearbyPair` | 가장 앞의 적부터 최대 2명 |
| `SkillRange.All` | 살아있는 모든 적 |

적 일반 공격은 플레이어가 공격 거리 안에 있는지만 보면 된다.
그래서 `EngageDistance`를 쓴다.

무공은 몇 명을 때리는지 봐야 한다.
그래서 `SkillRange`를 쓴다.

이 둘을 섞으면 "공격 가능한 거리"와 "맞는 대상 수"가 같은 개념처럼 보인다.
그러면 범위 무공이나 교전 거리 조정이 들어올 때 코드 의도가 흐려진다.

### 타겟 선택의 결정성

타겟 범위는 항상 같은 기준으로 골라야 한다.
같은 입력이면 같은 전투 결과가 나와야 하기 때문이다.

이번 코드의 타겟 선택 기준은 이렇다.

1. 죽지 않은 적만 남긴다.
2. `Position`이 작은 적을 앞쪽으로 본다.
3. 같은 `Position`이면 `Id`가 작은 적을 먼저 본다.
4. `SkillRange`에 맞춰 앞쪽 범위를 고른다.

`ThenBy(enemy => enemy.Id)`는 단순한 구현 장식이 아니다.
같은 위치에 적이 여럿 있어도 항상 같은 순서로 고르기 위한 결정성 규칙이다.

> [!note]
> `Where`, `OrderBy`, `ThenBy`, `ToArray`, `ReadOnlyMemory`의 자세한 C# 자료형 흐름은
> 필요할 때만 다시 보면 된다.
> Phase 4에서 오래 남길 핵심은 "살아있는 적을 앞쪽 순서로 결정적으로 고른다"는 규칙이다.

## 3. 중요한 상태 변경은 왜 한곳으로 지나가야 하나?

HP를 깎는 코드는 여기저기 흩어지면 위험하다.
어떤 곳은 HP를 0 아래로 내리고,
어떤 곳은 이벤트를 빼먹고,
어떤 곳은 죽은 대상을 또 때릴 수 있다.

그래서 중요한 상태 변경에는 출입문이 필요하다.
Phase 4에서는 HP 변경의 출입문이 `ApplyDamage`다.

`ApplyDamage`는 아래 규칙을 한곳에서 지킨다.

- HP를 0 아래로 내리지 않는다.
- 죽은 액터에게 데미지를 다시 적용하지 않는다.
- 데미지가 적용되면 `DamagePublished`를 보낸다.

이렇게 하면 데미지를 주는 원인이 늘어나도 HP 변경 규칙은 흩어지지 않는다.
적 일반 공격, 무공, 나중의 함정 데미지가 생겨도 같은 출입문을 지나가게 할 수 있다.

> [!important]
> 중요한 상태 변경은 한곳으로 모을수록 규칙을 빠뜨리기 어렵다.

## 4. 데미지 적용과 사망 확정은 왜 나누나?

데미지를 적용하는 순간 바로 `State = Dead`로 바꾸고 싶을 수 있다.
하지만 데미지 적용과 사망 확정은 서로 다른 일이다.

| 단계 | 하는 일 |
|------|---------|
| 데미지 적용 | HP를 줄이고 데미지 이벤트를 보낸다 |
| 사망 확정 | HP 0인 액터를 Dead로 바꾸고 사망 이벤트를 보낸다 |
| 결과 확정 | 승리나 패배를 한 번만 보낸다 |

이렇게 나누면 Tick 안에서 여러 시스템이 HP를 바꿔도,
사망 이벤트와 전투 결과는 정해진 위치에서 한 번만 정리된다.

이번 흐름은 이렇다.

1. 시스템들이 HP를 바꾼다.
2. Tick 끝에서 HP 0인 액터를 찾는다.
3. `State = Dead`로 바꾼다.
4. `ActorDeathPublished`를 한 번만 보낸다.
5. 승패를 확인한다.

> [!warning]
> HP가 0인 적은 아직 `Dead` 상태가 아니어도 이미 공격할 수 없는 적이다.
> 그래서 공격 시스템은 `State == Dead`뿐 아니라 `Hp <= 0`도 같이 봐야 한다.

## 5. 시스템 실행 순서와 이벤트 순서는 왜 게임 규칙인가?

순서는 단순한 구현 취향이 아니다.
같은 시스템과 같은 이벤트가 있어도 순서가 바뀌면 전투 감각과 결과가 달라질 수 있다.

Phase 4의 시스템 실행 순서는 이렇다.

1. `MovementSystem`
2. `EngagementSystem`
3. `CastingSystem`
4. `EnemyAttackSystem`
5. 사망과 승패 정리
6. `SnapshotPublished`

이 순서에는 의도가 있다.
먼저 이동과 교전을 정리하고,
그 다음 플레이어 무공을 시전하고,
HP가 남은 적만 일반 공격한다.
마지막에 죽음과 승패를 확정한 뒤 View에 Snapshot을 보낸다.

이벤트 순서도 규칙이다.
View, 테스트, 나중에 붙을 연출이 모두 이 순서에 기대기 때문이다.

Phase 4의 큰 이벤트 흐름은 이렇다.

1. `SkillCastPublished`
2. `DamagePublished`
3. `ActorDeathPublished`
4. `BattleResultPublished`
5. `SnapshotPublished`

이 순서가 있어야 "무공을 썼고, 데미지가 들어갔고, 그래서 죽었고, 그래서 승리했다"가 자연스럽게 읽힌다.

> [!note]
> 실행 순서와 이벤트 순서는 테스트가 우연히 관찰하는 로그가 아니다.
> 전투 시스템이 외부에 약속하는 규칙이다.
